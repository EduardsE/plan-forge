# PlanForge — implementation progress

Implementation of PlanForge from the design mockups (product context: see "What we're building" in `CLAUDE.md`) (`design/planforge-mockups.html` — open it in a browser to see all 4 screens side by side; screenshots in `design/screen-*.png`).

**How to use this file:** work on ONE task at a time, in order. Check off items as they land. Each task is sized to fit comfortably in a single Claude session. Phases 0–1 were static chrome; from Phase 2 on every task builds real functionality on a shared geometry model. The mockups define the *look*, not the implementation — their specific numbers and furniture become sample data, never hardcoded artwork.

## The design at a glance

A room/floor-plan editor. One full-screen workspace with four states shown in the mockups:

| Screen | What it shows |
|--------|---------------|
| 1a | 3D isometric "dollhouse" view, an object selected (context toolbar: rotate/duplicate/delete + dimensions) |
| 1b | Top-down 2D floor plan: walls, door arc, window, furniture footprints, dimension lines, room-area tooltip |
| 1c | Draw mode: wall-drawing tool stack, placed corners, segment length labels, inline length input, snap guides, cm/m units toggle |
| 1d | Objects panel: searchable furniture catalog with category chips, drag-out card, ghost placement footprint in 3D |

Shared chrome on every screen: dark navy left nav rail (Dashboard / Draw / Furnish / Objects / Views / Settings / avatar), project title + contextual status line top-left, floating undo/zoom toolbar, bottom-left 2D↔3D + grid/snap/fullscreen controls, bottom-right contextual readout chip (orbit/zoom, scale/grid, or snap mode).

**Visual language:** Space Grotesk (UI) + IBM Plex Mono (numeric readouts/chips), navy `#0F1B3D` / `#0C1430`, teal-cyan accent `#5EEAD4`→`#0EA5E9`, light blue-grey canvas `#F3F6FA` with grid lines, warm beige/terracotta room rendering, pill-shaped chips, big soft shadows.

## Phase 2 — Room model & rendering (both lenses, real data)

**Renderer decision (2026-07-09):** Three.js via `@react-three/fiber` + `@react-three/drei`, for **both** lenses. One scene graph, one raycaster, one world coordinate space; the 2D plan is the *same scene* under a top-down orthographic camera with plan-style presentation (flat materials, fat lines, drei `<Html>` DOM overlays for labels/inputs so text stays crisp and editable). Chosen over: pure-2D canvas libs (Konva/Pixi — can't do the 3D dollhouse), a hybrid SVG-2D + three-3D split (two render paths to keep in sync forever), and the mockup's CSS-transform approach (a dead end for real orbit/picking). This directly serves the product hinge: one model, instant lens switch.

- [x] Room geometry model (`src/lib/model/`): plain-data types — room outline (ordered corner list), walls derived as segments, openings (door/window = host wall + offset along it + width), placed furniture (catalog ref, position, rotation, W×D×H footprint) — plus pure helpers (wall lengths, floor area, outline bounds) with unit tests. Rendering-agnostic; every later task consumes this.
- [x] Sample room fixture matching the mockup's living room (6.40 × 5.20 m outline, one door, one window, desk / desk chair / credenza / shelf / rug / plant) so both lenses render real model data from day one — the "33.28 m²" must come out of the area helper, never be a string in a component.

- 2026-07-09: Animated 2D↔3D lens transition added (follow-up to the R3F canvas task). Technique: a dolly-zoom handoff — the perspective camera renders throughout the ~600 ms flight, easing between its orbit pose and a near-top-down pose (polar 0.01 rad; exactly 0 degenerates `lookAt` against the (0,1,0) up) while its fov narrows 42°→10° and distance grows to hold the frustum height at the floor plane constant; the swap to the true orthographic projection happens only at that matched endpoint, where it's imperceptible (`renderPlan` state lags the `planView` prop until landing). Pose interpolation tracks *frustum height at the target*, not distance, so fov and distance can change together without the room appearing to resize; the landing frustum height is pre-clamped to the ortho zoom limits so the swap never jumps. The orbit pose is saved on the way out and restored on the way back (verified: orbit to 27°/57°, round-trip through 2D, returns to exactly 27°/57°; mid-flight reversals continue from the current pose). The controls target moved to a persistent ref synced on every controls change, because OrbitControls remounts (keyed) on each lens swap — this is what makes 2D panning survive a 3D round-trip. The readout chip stays live mid-flight in the destination lens's units. Grid `fadeDistance` became one shared value (130) — a per-lens value pops mid-flight while the transition camera is ~40 m out. New pure helpers in `src/lib/camera.ts` (`frustumHeight`/`frustumDistance`, `wrapAngle`, `easeInOutCubic`), unit-tested. Browser-verification gotcha for later sessions: synthetic `PointerEvent`s dispatched from JS (non-primary pointer ids) make OrbitControls' `releasePointerCapture` throw `NotFoundError` — that's a test-harness artifact, use real Playwright `page.mouse` input instead.
