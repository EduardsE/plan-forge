# PlanForge — implementation progress

Implementation of PlanForge from the design mockups (product context: see "What we're building" in `CLAUDE.md`) (`design/planforge-mockups.html` — open it in a browser to see all 4 screens side by side; screenshots in `design/screen-*.png`).

**How to use this file:** work on ONE task at a time, in order. Check off items as they land. Each task is sized to fit comfortably in a single Claude session. The mockups define the *look*, not the implementation — their specific numbers and furniture are sample data, never hardcoded artwork.

## The design at a glance

A room/floor-plan editor. One full-screen workspace with four states shown in the mockups:

| Screen | What it shows |
|--------|---------------|
| 1a | 3D isometric "dollhouse" view, an object selected (context toolbar: rotate/duplicate/delete + dimensions) |
| 1b | Top-down 2D floor plan: walls, door arc, window, furniture footprints, dimension lines, room-area tooltip |
| 1c | Draw mode: wall-drawing tool stack, placed corners, segment length labels, inline length input, snap guides, cm/m units toggle |
| 1d | Objects panel: searchable furniture catalog with category chips, drag-out card, ghost placement footprint in 3D |

Shared chrome on every screen: dark navy left nav rail (Dashboard / Draw / Furnish / Objects / Views / Settings / avatar), project title + contextual status line top-left, floating undo/zoom toolbar, bottom-left 2D↔3D + grid/snap/fullscreen controls, bottom-right contextual readout chip (orbit/zoom, scale/grid, or snap mode).

**Visual language:** ~~navy chrome + teal accent + frosted glass~~ **superseded 2026-07-11 by the Paper redesign** (see Phase 6 below and "What we're building" in `CLAUDE.md`). Fonts stay Space Grotesk (UI) + IBM Plex Mono (numeric readouts); everything else moves to the light Paper palette with blue accent `#3A5BF0`. The 1a–1d screens above still define the *flows*; screens 2b/2d/3d define the *look*.

## Done: Phase 4 — Editing depth & persistence (each task verified headless; finished 2026-07-11, 254 unit tests + Biome clean)

Per-task implementation notes live in the git history (one commit per task); the load-bearing facts are compacted here.

- **Drag-to-move + 2D selection/manipulation:** one shared `MoveDragSession` (`src/components/move-drag.tsx`) drives both lenses — pick, drag with `snapPlacement` guides, chip follows live, esc restores (patch-based `FurnitureUpdate`; wall items get a mount branch).
- **Undo/redo:** `src/lib/history.ts` — bounded (100) snapshot stack with **commit / preview / settle** semantics: discrete mutations commit one step, continuous drags stream through `onRoomPreview` and fold into a single step on gesture end. ⌘Z/⇧⌘Z + toolbar buttons dim from `canUndo`/`canRedo`; history sits out draw mode (the draft is its own esc/⏎ session); localStorage hydration resets the stack.
- **Persistence:** `src/lib/persistence.ts` — versioned localStorage payload, paranoid deserialize (malformed → "no save"), post-mount hydration (no SSR localStorage), honest saved-at time, confirming **New room** as the only full wipe (clears to empty outline, drops into draw).
- **Door & window tools (2D lens):** `opening-tool-stack.tsx` arms insert-on-wall-click with ghost + corner-distance pills; placed openings drag along their wall (`plan-openings.tsx`) with flip-hinge/delete chip. Pure math in `opening-place.ts` (`slideOpening` quantizes + clamps into the nearest gap — overlaps impossible).
- **Draw edits the existing room:** the draft is `{ corners, closed, openings }` (`src/lib/outline-edit.ts`) — corners drag, walls split, length pills reshape via `setClosedSegmentLength`; commit (`applyOutlineDraft`) re-slides openings and keeps furniture whose rotated footprint still fits; leaving draw mode applies (never silently loses edits), esc reverts.
- **Draw stack finished:** rect tool (`rectangleOutline` in `src/lib/draw.ts`, two clicks → closed CW rectangle, hands off to Select); arc/split stubs deleted — `DrawTool` is `select | wall | rect`.
- **Grid / snap / fullscreen wired:** route-level `gridVisible`/`snapEnabled` + `workspaceRef`; a trailing `snap` param threads through all the pure snap functions (containment/clamp still applies when snapping is off); fullscreen targets the `.workspace-canvas` pane.
- **Object-to-object snapping:** placed items' rotated-footprint AABBs join `snapPlacement`'s nearest-line pipeline (`objectFaces` gates capture so flush neighbours never shove the mover into themselves), same teal guide pills; obstacles read through a ref so room churn doesn't resubscribe drag listeners.
- **Wall-mounted items:** optional `mount { wallIndex, offset, elevation }` on `FurnitureItem` (`model/wall-mount.ts`) — `position`/`rotation` are *derived* from the wall so all footprint code reuses them; `mount-place.ts` (`mountAt`, `reanchorMount`) snaps drops/drags to the nearest fitting wall and re-homes after reshapes.
- **Collision awareness:** `src/lib/collision.ts` — `containRoomFurniture` re-contains the mutated item on rotate/duplicate; `overlappingFurnitureIds` (SAT, 1 cm margin, rugs + mounts exempt) drives a soft red warning tint in both lenses.
- **Richer furniture meshes:** `src/lib/furniture-parts.ts` — `furnitureParts(catalogId, footprint)` composes box/cylinder/sphere parts **proportionally** from the footprint in bottom-relative local space with **+z = front**; per-id tailored builds → category fallback → plain box; colors in `FURNITURE_COLORS`; selection hull inflates per part (`partHullScale`).

## Phase 7 — Multi-room floors (COMPLETE — M1–M6 landed + verified 2026-07-11 → 2026-07-12)

**Requirement → deliverable.** "More than one room, connectable by doors/windows." Translated: a floor plan stops being one `Room` and becomes a **`Floor`** holding several rooms that share **one coordinate space**; a door or window sitting in a wall two rooms share is understood to connect them, and that connection is **derived from geometry, never stored** (consistent with "walls are derived, never stored"). This is a model-deep phase — it touches the model, persistence, history, both scenes, draw, and the inspector/status readouts — so it's sequenced after the Paper redesign (Phase 6) and the Phase 5 refinements settle. It supersedes the old "Deliberately not planned: multi-room floors" line.

**Design decisions (settled with the product owner 2026-07-11):**

- **Shared floor, no per-room origin offset.** Every room's outline/openings live directly in one floor coordinate space — you draw each room onto the same canvas, so there are no local↔world transforms to reconcile. `Floor { name?, rooms: Room[] }`; `Room` gains a stable `id` and keeps `{ name?, outline, openings, furniture }`.
- **No "active room" mode — the whole flat is the canvas.** Selection, move-drag, and the door/window tools all operate floor-wide against every room at once. "Which room" is *derived* (point-in-polygon) only where a readout is inherently per-room (a room's floor area) or an op is inherently per-room (drawing/reshaping one outline). Editing is never gated behind picking a room first.
- **Connection is derived, not a portal object.** An opening stays stored on one room's wall exactly as today. Where that wall segment abuts another room's wall (collinear + overlapping span), the opening is a *portal*: the neighbor's wall renders the matching cut and the shared wall isn't drawn solid/doubled. No `Portal` link is stored — abutment + span overlap is recomputed. (The rejected alternative — an explicit `Portal` referencing both rooms/walls — is cleaner for true adjacency but a far larger model + editing change; revisit only if derived seams prove too fragile.)
- **Furniture stays per-room** (least churn to `place.ts`/`collision.ts`/scenes). A piece belongs to the room whose outline contains its center; a drag that carries it across a seam **reparents** it (its own task, M5). Selection is global by furniture id regardless, so nothing about picking/inspecting changes.

**Honest-scope deferrals (deliberate):** no Z levels / stairs / multiple storeys (one floor plane); no per-room floor finishes or wall colors; no auto-detection of rooms from a single drawn boundary (you draw each room); room naming stays minimal/editable-later. **Dependency flag:** Phase 5's "Room settings: ceiling height + editable name" becomes *per-room* once `Floor` exists — if that task ships first it's written against a single room and generalizes here; if this phase ships first, that task lands per-room from the start.

## Conventions (everything builds on these)

- **All model lengths are meters**; cm/m is display-only (`src/lib/units.ts`). Furniture `rotation` is degrees CCW about the footprint center. Points are 2D plan coords — origin at the sample room's top-left, x right, y down — with heights as separate scalars; outlines wound clockwise (helpers tolerate either winding).
- **Walls are derived, never stored** (`wallsOf(outline)`); `Opening.wallIndex` indexes that derivation, plus `offset` along the wall, `width`, and optional `hinge` for the door swing. Wall/opening heights aren't modeled — they're mockup-measured constants in `src/lib/room-scene.ts` (wall 2.5 m × 0.1 thick, door head 2.05, window sill 0.36 / head 1.94).
- **Lib/component split everywhere:** pure math in `src/lib/*` with vitest coverage; rendering/interaction in `src/components/*`. The model stays renderer-agnostic (an SVG fallback for the 2D lens remains possible).
- **One R3F canvas** (`src/components/planner-canvas.tsx`), lazy-loaded client-only so three never runs during SSR. Both cameras stay mounted; drei `makeDefault` flips ortho↔perspective on the planView split (`"2d"`/`"draw"` ↔ `"3d"`/`"objects"`). The 2D↔3D switch is a ~600 ms dolly-zoom to a matched top-down endpoint before swapping to true ortho; scene presentation (`PlanScene` / `RoomScene` / `DrawScene`) switches on the same lagged `renderPlan` state, so the warm room stays up mid-flight.
- **Mockup numbers are sample data, never artwork:** 33.28 m² comes from `floorArea()`, the search placeholder counts real catalog items, selection readouts compute from footprints. The sample fixture was measured off the mockup canvases (110 px/m on 1b, 100 px/m on 1a). Known mockup inconsistencies deliberately not honored: 1a's chip text for the desk chair, 1d's guides-to-far-walls (we guide to nearest), decorative wall-art ticks.

## Gotchas (each cost real debugging time)

- drei `<Line>`: default alpha-to-coverage makes stroke quads resolve as opaque rectangles on this GPU stack — every plan stroke sets `alphaToCoverage={false}`, and dashes are pre-chopped into segments (`dashedPolyline`) because the dashed material misrenders the same way.
- drei `<Outlines>` renders nothing under drei 10 / three r185 (its `screenspace` mode explodes into a screen-filling hull) — the selection highlight is a hand-rolled inverted hull (same geometry +2 cm rim, cyan `meshBasicMaterial`, `side={BackSide}`).
- R3F pointer guards: only events whose DOM target is the actual `<canvas>` may deselect or place (drei `<Html>` clicks arrive as "pointer missed" / raycast through to the plane), and clicks that travelled > 4 px are orbit drags or pans, not clicks.
- The plan camera's straight-down pose reads as polar 90° in OrbitControls' up-relative frame — don't clamp `maxPolarAngle` in plan view; and exactly-0 polar degenerates `lookAt`, use 0.01.
- The objects drag never enters R3F's event system (pointer went down on DOM) — the ghost raycasts window pointermoves onto the y=0 plane manually. Wall-snap tolerance there is world-space (0.3 m): screen-px tolerance is depth-dependent under a perspective camera (draw mode's ortho snapping *is* screen-px based).
- Only furniture raycasts in the 3D scene (walls/platform/dressing set `raycast={() => null}`) — that's what makes furniture clickable behind visible walls.
- OrbitControls' `enabled` prop flushes too late to stop a gesture that begins on the same pointerdown (it eats the first pointermoves as orbit — the camera visibly drifts ~2°). The furniture move drag disables the controls *instance* synchronously in its pointerdown handler (`makeDefault` publishes it as `state.controls`); the prop only holds the steady state.
- Textures are module-cached CanvasTextures — safe only because the canvas module is lazy-loaded client-only.
- Browser verification: headless script with real `page.mouse` input (per CLAUDE.md — the MCP browser hangs on inactive macOS sessions, and synthetic PointerEvents make OrbitControls throw `NotFoundError`). Benign console noise: a `THREE.Clock` deprecation warning (drei 10 + r185). **Verify against the production build, not `pnpm dev`:** the TanStack devtools server-console forwarding catches that `THREE.Clock` warning in a feedback loop and re-echoes it with a growing `[Server]` prefix — tens of thousands of console messages within seconds, which pegs the page main thread (Playwright's in-page checks starve → `waitForSelector`/clicks time out even though the element "resolved to visible") and had ballooned a redirected dev log to 34 GB (filled the disk, which then made *everything* janky). `pnpm build && pnpm preview` (port 4173) has no console forwarding and drives cleanly.
- drei `<Line>` with `segments` + a long dashed loop (e.g. a rectangle's ~50 dash quads) stalls the render on this GPU stack — the rect-tool preview uses a **solid** (non-`segments`) `<Line>` loop instead, the same plain-Line pattern the committed outline uses. Short dashed *open* segments (wall preview, alignment guides) are fine.
- An *instant* down+up on an already-selected item (scripted `mouse.click`; a human click is slower) orphans a live `MoveDragSession`: the session's window listeners attach in a React effect, so a pointerup that lands before the effect runs is never seen, and the next mouse move drags the item with no button held (until the following pointerup ends the session). Pre-existing in the move-drag design, surfaced by the undo/redo verification — scripts should press-wait-release on selected items; a real fix would end the session from `handleMove` when `event.buttons === 0`.
- A leftover `pnpm preview` keeps serving the *old* server bundle after a rebuild (the SSR HTML then references client chunk hashes that 404) — and `pkill -f "vite preview"` doesn't match pnpm's process name. Kill it by port before re-verifying: `lsof -tnP -iTCP:4173 -sTCP:LISTEN | xargs kill`.
- The `@tanstack/devtools-vite` plugin's click-to-source injection is turned **off** in `vite.config.ts` (`injectSource: { enabled: false }`): it stamps `data-tsd-source` on every JSX element, and R3F reads hyphenated props as nested paths (`data-tsd-source` → `object.data.tsd.source`), so the attribute threw "Cannot set data-tsd-source" and tripped the canvas error boundary whenever a scene element mounted (e.g. during a furniture drag). Don't re-enable it without scoping every three.js-rendering file out.
